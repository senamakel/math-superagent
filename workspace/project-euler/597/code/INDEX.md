# Index — code

What each file in this folder is for. Keep it current: describe a file when you create it, and refresh this index after adding, renaming, or deleting files.

| `AGENTS.md` | Folder convention doc for code/: every program lives here and its output in code/out/; how to describe programs in the index (say what establishes correctness: examples reproduced, brute agreement, size reached); one job per file, exact arithmetic, never delete a program carrying a result. |
| `arrangement_pn.py` | EXACT arrangement oracle for p(n,L) at n=3 and n=4, over integer L. Uses the fact that common scaling of the Exp(1) speeds preserves the race outcome, so p(n,L)=(n-1)!·(Euclidean measure of even-parity cells) on the unit speed simplex in free coordinates. Enumerates the cells of the linear arrangement of all candidate-event-time equalities (finish times F_j=(L-40j)/v_j, catch times C_ab=40(b-a)/(v_a-v_b), and v_a=v_b lines) by polygon clipping (2D, n=3) / polyhedron vertex+volume enumeration (3D, n=4), evaluates the exact race at each cell centroid via exact_race.outcome_parity_exact, and sums exact cell areas/volumes. Anchor checks p(3,160)=56/135 and p(4,400)=0.5107843137 built in; writes code/out/exact_pn.json. The exact (non-exhaustive-MC) solver, giving exact rationals the faster/nonexact methods are checked against for n=3,4. |
| `brute.py` | Naive exact oracle for PE 597: chronological race simulation + parity of the new order derived from bump chains. Exposes `simulate_order`, `parity_of_new_order`, `outcome_parity`. Reproduces all five rows of the n=3,L=160 table. Uses full-reachability `above` (the multi-bump edge-loss bug is fixed), so it is the reference-correct engine — byte-identical in dynamics to `simulate_order_nobug.py`. |
| `bump_forest.py` | TASK 2. Returns the bump forest as a parent array (`parent[j]=k` when boat j bumped k, None for finishers); each boat bumps at most once so `parent[]` is a valid parent array. Verifies over N=1e6 trials at n=3,L=160 that the forest ancestor-descendant-pair count mod 2 equals `brute.outcome_parity` — the parity == (# bumped chain pairs) correspondence. MC verifier, not a solver. |
| `bump_study.py` | Monte Carlo structural study (small n, L=160): for each sample records parity, bump multiset, finishes, chain-pair count; verifies `parity == (#chain pairs) mod 2` on every sample and histograms bump-pattern types split by parity. MC driver, not a solver. |
| `cell_exact.py` | Compact exact-cell enumerator for p(n,L) (n<=4 oracle), the same arrangement strategy as arrangement_pn.py/p_cell_exact.py but self-contained: normalizes speeds to the (n-1)-simplex, slices cells via toolkits arr_enum.enumerate_cells + leaf_interior, reads parity at each cell interior with exact_race.outcome_parity_exact, and sums exact even-cell volumes times (n-1)!. Correctness anchored inside: reproduces p(3,160)=56/135 and p(4,400)=521/1020=0.5107843137, and prints cell counts (n=3->32 cells, n=4->1202). Exact solver, not MC. |
| `check_counterexample.py` | Sanity/oracle check: validates the counterexample pair ce1/ce2 (n=3) give opposite parities with float and exact agreement, and prints uniform-grid even-count ratios for M in (8,16,32). Grid converges to 0.5, not 56/135 — a sampling-measure artifact (uniform grid ≠ Exp(1)), not a parity bug. |
| `check_p3_formula.py` | Validation script for the conjectured closed form p(3,L)=(7m^2-17m+12)/(18m^2-45m+27), m=L/40, checked against every exact p(3,L) point (12 from exact_p3_data.DATA + 16 extra L hard-coded here), printing per-L match, total mismatches, and the m→∞ limit 7/18. Tests the exact-arrangement values; not a solver. |
| `cross_decoupling_test.py` | Decisive test (Q1/Q2/Q3, N=200k default) of the research-library treap recursion for PE 597 against the true race oracle: Q1 asks whether cross (left/right index pairs joined by a bump chain) ALWAYS equals left-count times right-count; Q2 whether cross depends only on the min-W root identity (decoupling); Q3 whether parity(left)*parity(right)*(-1)^cross with TRUE cross reproduces the oracle (tautological). Diagnostic of the treap recursion hypothesis, not a solver. |
| `cross_direct_test.py` | Direct test of the two decisive treap claims at the root: (a) is cross == r*(n-1-r) always?, and (b) is cross constant across speed vectors sharing the same min-W root? Counts violations against the true race oracle across (n,L) configs. Diagnostic of the treap hypothesis, not a solver. |
| `crux_decoupling_test.py` | Crux decoupling test (N=300k default) of the treap hypothesis for PE 597: D1/D2 ask whether parity of the left/right sub-range in the final permutation equals the sub-race oracle parity on that slice; D3 whether true cross equals left-times-right; D4 whether recursion(true cross, true sub-race) reproduces full parity; plus per-root cross-value dispersion. Diagnostic of the treap recursion, not a solver. |
| `exact_p3_data.py` | Data module only: exact rational p(3,L) (fraction even) for 12 integer L (160,…,1800) from the exact n=3 arrangement enumeration, held as DATA = {L: "num/den"}. Imported by check_p3_formula.py and fit_p3*.py as the reference exact values; the __main__ prints them as floats. |
| `exact_p3_extra.py` | Validation-oracle driver for PE 597, n=3 only: exact p(3,L) for the 16 extra integer L (120,200,280,360,440,520,560,720,900,1100,1400,2000,2400,3000,4000,5000) by the exact arrangement enumeration (simplex slicing, exact rational, parity at cell centroids via exact_race.outcome_parity_exact). First re-derives and asserts all 12 known anchors from exact_p3_data.DATA (56/135 ... 2237/5742), then writes code/out/exact_p3_extra.json as {"L": {"p": "num/den", "ncells": int}}. Established correct: all 12 anchors reproduced EXACTLY; every value independently reproduced by the second enumerator p_cell_exact.py/arr_enum.py; MC (400k) within 1 SE. |
| `exact_p4_data.py` | Exact p(4,L) data module: L→p(4,L) as exact rational strings for 4 integer L (160..400), captured from the n=4 arrangement enumeration (snapshot of earlier JSON). Includes the anchor p(4,400)=521/1020=0.5107843137. Data reference, not a solver. |
| `exact_race.py` | Exact-rational race dynamics mirroring the fixed `brute` on Fractions (`simulate_order_exact`, `outcome_parity_exact`); tuple-vs-Fraction comparison bug fixed so it runs. Uses full-reachability `above` like the fixed `brute`. |
| `examine_multibump.py` | Retired diagnostic that once demonstrated the multi-bump overwrite bug in `brute.simulate_order`: `bumped_by[k]` kept only the last bumper, silently losing earlier bump edges. | `fit_p3.py` | Exploratory fitter: tries to fit the exact p(3,L) values from code/out/exact_pn.json to a rational function N(L)/D(L) with low degrees (via sympy exact solving), validates by residuals and attempts the L->inf limit. Probing whether p(3,L) has a simple closed-form rational shape. Diagnostic/exploratory; not a solver. |
| `fit_p3_sympy.py` | Exploratory exact fitter for p(3,L): treats p3(m)=N(m)/D(m) in m=L/40 as a rational function with small-degree polynomial numerator/denominator and solves exactly for the coefficients via sympy on enough data points, then checks all points in exact_p3_data.DATA. Probes whether p(3,L) has a simple closed-form rational shape in L. Diagnostic/exploratory, not a solver. |
| `high_precision_mc.py` | High-precision parallel Monte Carlo for p(n,L) using the verified `brute.py` engine. Each worker runs its own RNG seed and chunk; results pooled with binomial-mean SE. Usage: `python3 high_precision_mc.py n L total_samples` (one process per (n,L)). MC estimator, not exact. |
| `largeL_limit.py` | True large-L limit p(n,L) as L->inf by MC on the real Exp(1) dynamic (brute engine), for n in 3..6 at L in {1e5,1e8}. | `p2_verify.py` | Verifies the derived exact closed form for n=2: p(2,L)=L/(2L−40). Boat0 bumps boat1 iff v0/v1 > L/(L−40), so P(bump)=(L−40)/(2L−40) and p(2,L)=1−P(bump)=L/(2L−40). Checks the closed form against the brute oracle by high-N Exp(1) MC at L in (48..40000). Validation check for the exact method, not a solver. |
| `p3_inf_mc.py` | Exploratory exact/rational + MC script for p(3,infinity), the pure bump race with NO finish line (L infinite). Partly scaffolded (a separating-times helper is stubbed out); used to probe the no-finish (speed-order-only) limit. Exploratory diagnostic, not the full-size solver. |

Second route confirming the arrangement solver's p(3,L). |
| `p4_mcverify.py` | Independent MC cross-check of exact p(4,L) values from code/out/exact_pn.json using the brute.py engine directly (n=4, L∈{160,240,320,400}), including the anchor p(4,400)=0.5107843137. Cross-engine validation of the n=4 exact oracle; not a solver. |
| `p_cell_exact.py` | Exact rational integration oracle for p(n,L) over the speed simplex (Monte-Carlo-free). Shares the arrangement approach: normalized speeds are uniform on the (n-1)-simplex, p(n,L) = (n-1)!·(Euclidean volume of even-parity cells), with the outcome's separating set a genuine straight-line hyperplane arrangement (every candidate time const/(affine), so pairwise time-equalities are affine). This file is the driver that ties together toolkits/arr_enum.enumerate_cells (cell slicing), toolkits/arr_polytope (exact volume), and exact_race.outcome_parity_exact (strict-interior parity), summing even-cell volumes. Usage: `python3 p_cell_exact.py n L`. Exact solver for n=3,4 (companion to arrangement_pn.py; both implement the same arrangement strategy with different cell machinery). |
| `parity_recursion.py` | Implements the claimed range-parity recursion borrowed from CONTEXT.md/research (root = argmin of W_i = v_i/(L-40i) over the index range, parity = left*right*(-1)^cross) and tests it against the brute oracle outcome_parity on random Exp(1) speed vectors.
